## Что уже готово в Godot

`scripts/game/unit_index.gd` в сохранённом Godot-репозитории, commit `523daab5bbafe0bac24bc9758435c4e3f90cb9b6`: CELL=12, buckets/members/formations, поиск только нужных ячеек, проверка точного радиуса, сохранение исходного порядка при равных целях, обновление индекса при перемещении, invalidate при изменении состава. Для глобального радиуса предусмотрен обычный обход массива вместо тысяч пустых ячеек. Копия прочитана в `work/nerubian033/godot-source/unit_index.gd`.

Это полезная основа для Unity. При переносе нужно обновлять индекс также при скачке, захвате, рождении, смерти и смене полёта; сохранять прежний порядок разрешения событий. Простая сетка всё ещё имеет квадратичный худший случай, если вся армия сжалась в несколько ячеек.

## Что обнаружено в Unity

- `HumanCombat.TickUnitCore`: поиск в Units, дорогой WeaponFor выполняется до проверки расстояния, затем OrderBy. Это повторяется для множества бойцов, включая далёких врагов.
- `GroundSeparation033`: обход Units для каждого движущегося наземного бойца. В текущем исправлении есть дешёвое исключение дальше 4 единиц перед проверкой статусов/JSON; полный линейный обход пока остаётся.
- `FindUnit`: FirstOrDefault по Units; снаряды повторяют такие поиски владельца/цели несколько раз. Нужен индекс id→Unit без изменения порядка основного списка.
- `TryAutocast`/Cast и отдельные расовые обработчики используют общие поиски, LINQ и JSON. Ауры уже обновляются раз в .5 с; в данном составе они занимают значительно меньше времени, чем решения/движение. Это не результат теста армии с множеством разных аур.
- `MechPowered` перебирает все Huts при проверке каждого здания, в том числе когда электростанций вообще нет. Это даёт квадратичный обход построек и объясняет отдельный приоритет индекса источников питания/зон. Нужен список реально существующих источников и ранний выход при его пустоте; проверка только по выбранной расе неверна для Ultimate и захваченных зданий.
- `PcGame.Update`: симуляция .05 с, при накоплении времени несколько Tick подряд. Если один Tick уже слишком дорогой, следующий кадр пытается догнать время и ещё сильнее задерживает показ. Просто отбрасывать тики нельзя: это меняет длительность заклинаний, производство и результат боя.
- `ArmyLimit=160` на сторону ограничивает обычное производство; прямое создание для стресс-теста сознательно превышает этот лимит. Призывы требуют отдельного учёта. Предел в этом аудите не изменялся.

## Варианты и порядок работ

| Порядок | Изменение | Ожидаемый эффект | Цена/риск |
|---|---|---|---|
| 1 | Пространственный индекс по образцу Godot + id→Unit; расстояние до дорогих фильтров; ближайшая цель одним проходом без OrderBy | Убирает большую часть далёких пар и повторных id-поисков, сохраняет частоту боя | Нужно точно сохранять дальность, невидимость, воздух, иммунитеты, равные цели и порядок появления |
| 2 | Типизированные неизменяемые данные способностей/оружия; кэш состава активных умений; повторное использование буферов | Меньше JSON/строк/LINQ и кратковременных объектов в горячих циклах | Изменение ранга/баффа/захвата должно инвалидировать нужный кэш |
| 3 | Сохранять живую допустимую цель; распределить повторный поиск по 4–8 Гц; редкие проверки бездействующих и застрявших | Сглаживает пики и уменьшает количество решений | Изменяет задержку реакции, поэтому требует отдельного согласования поведения. Готовую атаку и попадание всегда перепроверять немедленно; не задерживать смерть, иммунитеты и таймеры |
| 4 | Планировщик времени производства/готовности заклинания/срока эффекта; отдельные активные списки | Масштабирование при множестве построек и редких событиях | Одинаковое время событий должно разрешаться стабильно; мана, перенос яда, отмена и пауза усложняют расписание |
| 5 | Jobs + Burst для независимой математики, поиска кандидатов, движения; последовательное применение попаданий | Использование нескольких ядер после подготовки данных | Нельзя передать текущие JObject, List<Unit>, Unity API и взаимозависимые DamageUnit прямо в Job. Полный ECS — отдельный дорогой вариант |

Я предлагаю начать с **первого и второго пунктов**, затем повторить те же сценарии и только по результату решать про частоты и Jobs. Боевой лимит/производство/урон не использовать как скрытую «оптимизацию». Для густого фронта дополнительно понадобятся локальная структура соседей/линейная организация по узкой дороге и ограничение повторных запросов, а не надежда на одну сетку.

Проверка изменения: одинаковые seed и последовательность приказов до/после, сравнение допустимых/выбранных целей, HP/маны/смертей/выпуска и снарядов; отдельные случаи воздуха, невидимости, продажи/захвата, массовых AoE, разных сторон. Затем измерение 320/500/1000/2000 юнитов и массового выпуска в фактическом Windows player и на Android, с p50/p95/p99 времени тика и измерением GC.Alloc рабочим профайлером. Сначала добиться тика с запасом внутри 50 мс; целевой внутренний бюджет логики для 60 FPS следует назначать по реальным устройствам, например 5–8 мс, а не обещать FPS заранее.

## Первичные внешние источники

- [Unity: Job system overview](https://docs.unity.com/en-us/engine/6000.5/manual/scripting/optimization/job-system/overview): потоки, Burst и ограничения blittable-данных. Применение к нашему проекту выше — инженерное предложение.
- [Unity: управление сборщиком мусора](https://docs.unity.cn/6000.0/Documentation/Manual/performance-disabling-garbage-collection.html): отключение GC не отменяет выделения и приводит к росту памяти; это не предлагаемое решение.

Основные выводы о Castle Fight основаны на непосредственно проверенном архиве карты и коде обоих переносов. Закрытые внутренности Warcraft по обсуждениям на форумах не выдаются за установленный факт.
